# AI エージェント作業基盤 セットアップキット

このリポジトリ（sh-ltv-3）で育ってきた **CLAUDE.md / AGENTS.md / `.claude/skills` / `docs` の作業基盤**を、
別のリポジトリでも短時間で立ち上げ直すための移植用ドキュメントです。

「特定リポジトリ用の設定ファイル」ではなく、**同じ構造を再生成するための設計仕様＋手順書**として書いてあります。
sh-ltv-3 固有の名前・パス・技術スタックはそのまま持ち込まず、対象リポジトリの実態に合わせて作り直してください。

---

## 0. このファイルの使い方

### 人間向け

1. このファイルを対象リポジトリの `docs/`（無ければ任意の場所）にコピーする。
2. AI エージェントに次のように指示する:

   > `docs/ai-scaffolding-kit.md` を読んで、このリポジトリ用に
   > `CLAUDE.md` / `AGENTS.md` / `.claude/skills` / `docs` の作業基盤を整備して。
   > まずリポジトリを調査してから、キットの設計思想に沿って作ること。
   > 作った skill は description を「いつ使う / いつ使わないか」の観点で見直して。

3. AI が提案した skill 構成をレビューし、過不足を伝えて調整する。

### AI エージェント向け（前提ルール）

- **まず対象リポジトリを調査してから作る。** ディレクトリ構成・主要言語・技術スタック・既存の規約ドキュメント・テスト配置・CI を把握する前に生成物を書かない。
- **このキットのサンプル名（sh-ltv-3, apps/web, FRONTEND_GUIDELINES.md 等）をそのまま出力しない。** すべて対象リポジトリの実在する名前・パスに置き換える。
- **推測でルールを書かない。** リポジトリに存在しない規約・コマンド・パスを skill に書かない。確認できないものは「未確定」として人間に確認する。
- **一度に全部作らず、構成案 → 合意 → 生成の順で進める。** 特に「どの skill を作るか」は人間の合意を取る。

## 2. 設計思想（ここが本体）

構造をコピーするだけでは機能しません。以下の原則を守ることで「育つ基盤」になります。

### 2.1 正本を一元化する（CLAUDE.md はミラー / 正本は AGENTS.md ）

- 規約の本体は AGENTS**.md にだけ書く**。
- `CLAUDE.md` は「AGENTS.md を読め」と誘導するだけにして、内容を複製しない。
- 理由: 規約を 2 箇所に書くと必ずズレる。原本を 1 つに固定する。

### 2.2 SKILL.md は薄いルーター、詳細は references に逃がす

- `SKILL.md` 本体は「この作業では**何を先に読み**、**どの順で判断し**、**何をしないか**」を短く書く。
- 具体的な作法・テンプレ・長い規約は `references/*.md` に分け、**必要なときだけ読ませる**。
- 理由: SKILL.md は description で常時ロードされうる。分厚いと毎回コンテキストを食う。詳細は「読む条件」とセットで分離する。

### 2.3 description は「いつ使う / いつ使わない」を書く

- frontmatter の `description` は要約ではなく**ルーティング判定材料**。
- 「どういう依頼で使うか」に加えて、**「どの依頼では使わないか（＝別 skill の領分）」**まで書く。
- 理由: skill が増えるほど誤発火が問題になる。使い分けの境界を description に書くと選択が締まる。

### 2.4 リポジトリ本体の長文ガイドは skill から「指す」

- 既に `FRONTEND_GUIDELINES.md` のような詳細規約が本体にあるなら、skill にコピーせず**パスで参照**する。
- skill は「まず reference を読み、次に本体ガイドを読む」という**読む順序**を与える役に徹する。
- 理由: 規約の原本はコード近くの本体ドキュメント。skill は導線であって規約の再定義ではない。

### 2.5 コンテキストを節約する（生データを本スレに載せない）

- 差分レビューのような重い作業は、**入れ子サブエージェント**で下層に閉じ込め、本スレには結論だけ返す。
- 「出す役（指摘）」と「反証する役（検証）」を分けて誤検知を落とす、なども同じ発想。
- 理由: 本スレのコンテキストは有限。生データ・検討過程は下層で完結させる。

### 2.6 チャット外に永続化する（branch memo / task spec）

- 長期タスクの背景・仕様・調査結果は**チャット履歴ではなくファイル**に書く。
- 新しいチャットは、長い履歴を遡る前に**まず memo / spec を読む**。
- 理由: チャットは流れて消える。引き継ぎコストと再調査コストを下げる。

### 2.7 確定と未確定を混ぜない

- task spec では「確定仕様」と「未確認事項」を**セクションで分ける**。推測を確定仕様に昇格させない。
- 証拠（ファイルパス・関数名・テーブル名・回答日）を添える。
- 理由: 後から読む人（＝別チャットの AI や自分）が、何を信じてよいか判断できる。

### 2.8 クロスツール可搬性（任意）

- 複数の AI ツールを使うなら、`agents/*.yaml` に表示名・起動プロンプトを置き、同じ skill を各ツールから呼べるようにする。

## 3. セットアップ手順（AI が順に実行する）

### Step 1. リポジトリ調査

以下を把握してからでないと書き始めない。

- ルートのディレクトリ構成（モノレポか / `apps/*` `packages/*` の有無）
- 主要言語・フレームワーク・パッケージマネージャ・ランタイム
- 既存の規約ドキュメント（`GUIDELINES*.md`, `CONTRIBUTING*`, `README` の作法節など）
- テストの配置と実行コマンド（`package.json` scripts / Makefile / CI 設定）
- lint / typecheck / build のコマンド
- 「繰り返し発生する作業」の種類（実装 / テスト / レビュー / 運用手順 など）

### Step 2. CLAUDE.md を作る

§4.1 のテンプレを土台に、対象リポジトリ用に:

- 行動原則（例: 「コードを読まずに書かない」）を書く。
- **作業範囲の制限**（指示された修正のみ / lint・test・build は依頼時のみ 等）を明記する。
- **Project Skills ルーティング表**を書く（どの作業でどの skill を使うか）。まだ skill が無ければ Step 5 の後に追記する。
- 作業メモ（branch memo / task spec）の運用ルールを書く。

### Step 3. AGENTS.md を作る

§4.2 のテンプレ通り、**CLAUDE.md を指すだけ**にする。内容を複製しない。

### Step 4. どの skill を作るかを設計（人間の合意を取る）

「このリポジトリで**繰り返し発生し、毎回同じ作法が要る作業**」を洗い出して skill 候補にする。
汎用的な初期セット（§6）を出発点に、対象リポジトリで不要なものは削り、特有の運用作業を足す。
**この一覧を人間に提示して合意を取ってから**生成に進む。

### Step 5. skill を作る（SKILL.md + references）

各 skill について:

1. §4.3 の frontmatter で `name` と `description`（いつ使う / いつ使わない）を書く。
2. SKILL.md 本体は**薄いルーター**にする（先に読むもの・判断順・やらないこと）。
3. 長い作法・テンプレは `references/*.md` に分け、「いつ読むか」を SKILL.md に書く。
4. 本体に既存の詳細ガイドがあれば**パスで指す**（複製しない）。

### Step 6. docs 基盤を作る

- `docs/branch_memo/` を作り、運用ルールを CLAUDE.md に書く（§4.6）。
- `docs/task-specs/task-spec-template.md` を置く（§4.5）。

### Step 7. 見直し

§5 のチェックリストで全 skill を点検する。特に description の使い分けと、SKILL.md が薄いかを確認する。

## 4. テンプレート集

> プレースホルダ（`<...>`）は対象リポジトリの実値に置き換える。日本語/英語はリポジトリの既存言語に合わせる。

### 4.1 CLAUDE.md

```markdown
# CLAUDE.md

このファイルを原本とし、`AGENTS.md` はこのファイルへのリンク／ミラーとして扱う。

## 行動原則

-3 ステップ以上のタスクは Plan モードで開始する（※使っているツールに応じて）-コードを読まずに書かない。必ず既存コードを確認してから変更する

## 作業範囲の制限

-指示された修正のみを実施する。-明示的に依頼されていない調査・追加修正・改善提案・リファクタは行わない。
-lint / test / build は、ユーザーが明示的に依頼した場合のみ実行する。-修正完了後は追加作業を始めず、変更内容を簡潔に報告して停止する。-判断に迷う場合は、勝手に進めずユーザーに確認する。

## Project Skills

-<実装・修正・リファクタ> では `.claude/skills/<impl-guide>/SKILL.md` を使う
-<テスト追加・修正> では `.claude/skills/<test-writing>/SKILL.md` を使う
-<差分・PR レビュー> では `.claude/skills/<code-review>/SKILL.md` を使う
-<長期タスクの仕様整理・引き継ぎ> では `.claude/skills/<task-spec-manager>/SKILL.md` を使う

## ブランチ作業メモ

-新しいブランチで作業を始めたら `docs/branch_memo/` にブランチ名と同名の Markdown を作る
（`/` は `_` に置換）。-作業中は継続的に更新し、チャット履歴ではなくこのファイルを作業記録・仕様書として扱う。-記録内容: 作業目的 / 背景 / 確定仕様 / 未確認事項 / 調査結果 / 実装方針 / 実装内容 /
レビュー重点 / 残課題 / 作業ログ。-推測は「確定仕様」に書かず「未確認事項」または「調査結果」に記録する。-作業完了後も削除せず作業履歴として保持する。
```

### 4.2 AGENTS.md

```markdown
# AGENTS.md

このリポジトリのエージェント向け規約の**正本は CLAUDE.md**。
AGENTS.md を参照するツール（Codex / Cursor / 他エージェント等）は、CLAUDE.md を読み、その内容に従うこと。
```

### 4.3 SKILL.md（薄いルーター型）

```markdown
---
name: <skill-name>
description: <対象リポジトリ> で <どの作業> をするときの skill。<いつ使うか>。<どの依頼では使わないか（別 skill の領分）> は含めない。
---

# <Skill Title>

この skill は <この作業> の入口。変更対象に応じて必要な reference だけ読んでから作業する。

## 共通

-変更対象の既存コードを先に読む -既存責務に寄せて実装し、新旧パターンを不用意に混在させない
-<このリポジトリ特有の最低限ルールを 2〜4 個>

## 先に読むもの / 対象別の読み方

-<領域A> を触るときは、まず `references/<a>.md` を読み、その後 `<本体ガイドのパス>` を確認する
-<領域B> を触るときは、まず `references/<b>.md` を読む -今回の変更に関係ない reference までは読まない

## 進め方

1.<ステップ1>
2.<ステップ2>
3.<...>
```

```markdown
-<アンチパターン>

-<既存の実例ファイルパス>
```

## 5. skill 見直しチェックリスト

新規/既存 skill を点検するときの観点。

- [ ] `description` に**「いつ使うか」**が書いてある
- [ ] `description` に**「いつ使わないか（別 skill の領分）」**が書いてある
- [ ] SKILL.md 本体が**薄い**（詳細が references に逃げている）
- [ ] references は**「いつ読むか」の条件付き**で参照されている
- [ ] 本体に既存ガイドがある規約を**複製せず、パスで指している**
- [ ] 書いてあるパス・コマンドが**対象リポジトリに実在する**
- [ ] skill 同士の**役割が重複していない**（境界が description で切れている）
- [ ] sh-ltv-3 など**移植元固有の名前が残っていない**
- [ ] CLAUDE.md の **Project Skills ルーティング表**に登録されている
- [ ] 推測・未確認の規約を**確定ルールとして書いていない**

## 7. よくある失敗

- **SKILL.md に規約を全部書く** → 毎回コンテキストを食う。詳細は references へ。
- **description が要約だけ** → 誤発火する。使い分けの境界を書く。
- **AGENTS.md に規約を複製** → CLAUDE.md とズレる。ポインタに徹する。
- **移植元の名前が残る**（sh-ltv-3, apps/web 等）→ 対象リポジトリの実値に必ず置換。
- **存在しないパス/コマンドを skill に書く** → 調査してから書く。無ければ人間に確認。
- **skill を勝手に量産** → まず候補一覧を提示して合意を取る。
