# Task Spec 更新ルール

`docs/task-specs/<slug>/task-spec.md` を書く・更新するときの詳細。テンプレは
`docs/task-specs/task-spec-template.md`。

## 確定 / 未確認の分離

spec のいちばんの役割は「後から読む人が、何を信じてよいか」を判断できること. だから
セクションで確定と未確認を必ず分ける。

- **確定仕様**: 確認済みの事実のみ。証拠が添えられるものだけ書く。
- **未確認事項**: 未決定・確認待ち・仮定。ここに書いたものは「まだ信じてはいけない」印。
- 迷ったら未確認側に置く。**推測を確定仕様へ昇格させない。** 昇格させてよいのは、
  証拠（下記）で裏が取れたときだけ。

## 証拠の付け方

確定仕様・調査結果には根拠を添える。最低限どれか一つ:

- 実在するファイルパス（例: `src/core/apply.ts`）
- 関数名 / 型名 / schema 名（例: `applyChanges()` / `truer.proposal.v0`）
- 外部プロジェクトの位置（例: `C:\Users\kannn\Seamlint` の `slnt check` 出力）
- 人への確認なら「回答日」と回答内容（例: 2026-07-11 回答: apply の書き先は `--out` のみ）

## セクションの書き方

- **目的 / 背景**: なぜこのタスクが要るか。1〜3 行で。
- **確定仕様**: 上の分離ルールに従う。
- **未確認事項**: 疑問・仮定・確認待ちを箇条書き。解決したら確定仕様へ移し、証拠を添える。
- **関係者への確認状況**: 状態を明示（未確認 / 確認待ち / 回答あり / 要再確認 / 対応済み / 実装保留）。
- **既存実装の調査結果**: 現状の挙動と、「変える / 変えない」方針を分けて書く。
  Truer の invariant（propose は source を書かない、preview と apply の一致 等）に関わる部分は、
  AGENTS.md の「常に守る境界」と矛盾しないか確認する。
- **実装方針 / 変更ファイル**: 確定した計画があるときだけ具体化する。無いなら空でよい。
- **テスト観点**: 変更で守りたい仕様、落ちると何が壊れるか。
- **作業ログ**: 日付き（`YYYY-MM-DD`）で追記していく。上書きしない。
- **次にやること**: 別チャットが即再開できる粒度で書く。

## 避けること

- 確定仕様と未確認事項を同じ箇条書きに混ぜる。
- 証拠のない断定を「確定仕様」に書く。
- Truer の実装作法・invariant をここに複製する（正本は AGENTS.md と
  `.claude/skills/truer-implementation/references/`。spec からは参照するに留める）。
- 完了後に spec を削除する。履歴として残す。

## branch memo との使い分け

- ブランチ単位の作業ログ・handoff は `docs/branch/<branch>.md`（`.claude/skills/branch-worklog/`）。
- 複数ブランチ・複数セッションにまたがるタスクの「確定した仕様書」は task spec。
- 片方に書いたことをもう片方へ機械的にコピーしない。長期の確定仕様は task spec を正とする。
